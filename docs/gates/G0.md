# Gate G0 — rlib embedding ✅ PASS

**Date:** 2026-05-29  
**Spike crate:** `crates/warp-drive-g0-spike`  
**Status:** DONE. The gate condition is demonstrably true.

---

## Gate condition

> Native Rust binary links `warp-wasm` as an rlib; `init_embedded()`
> initializes the engine kernel; one `observe_cbor()` round-trips from
> outside the echo workspace.

All three conditions passed in a single run of the spike binary.

---

## What was proved

### 1. rlib embedding works

`warp-wasm` compiles to a native Rust rlib when the `engine` feature is
enabled. A binary in a **separate Cargo workspace** (`warp-drive/`)
links it as a path dependency through the `echo-warp-drive` worktree:

```toml
[dependencies]
warp-wasm = { path = "../echo-warp-drive/crates/warp-wasm", features = ["engine"] }
```

No wasm runtime (wasmtime, wasmer, etc.) is required. The rlib is a
plain Rust library; the FUSE binary links it the same way it links any
other crate.

### 2. `init_embedded()` initializes the engine kernel

Real signature (from `crates/warp-wasm/src/lib.rs`):

```rust
pub struct EmbeddedHandle {
    pub worldline_id: WorldlineId,
    pub head: HeadInfo,
}

pub fn init_embedded() -> Result<EmbeddedHandle, AbiError>;
```

Usage from the spike:

```rust
let handle = warp_wasm::init_embedded()?;
// handle.worldline_id         — the default worldline UUID
// handle.head.worldline_tick  — first tick (0)
// handle.head.state_root      — initial Merkle root (non-zero)
// handle.head.commit_id       — genesis commit id
```

`init_embedded()` creates a `WarpKernel`, installs it as the global
kernel singleton, bootstraps capabilities, and returns the default
worldline id plus the initial head. Capability bootstrap, kernel init,
and error propagation all work across the workspace boundary.

### 3. `observe_cbor()` round-trips

```rust
// Build a one-shot ObservationRequest for the default worldline
let request = ObservationRequest::builtin_one_shot(
    ObservationCoordinate {
        worldline_id: handle.worldline_id,
        at: ObservationAt::Frontier,
    },
    ObservationFrame::CommitBoundary,
    ObservationProjection::Head,
)?;

// Encode → call → decode
let request_bytes  = echo_wasm_abi::encode_cbor(&request)?;  // 254 bytes
let response_bytes = warp_wasm::observe_cbor(&request_bytes);
let artifact: OkEnvelope<ObservationArtifact> =
    echo_wasm_abi::decode_cbor(&response_bytes)?;
```

The 254-byte CBOR request returns a valid `OkEnvelope<ObservationArtifact>`
with a non-empty `artifact_hash` and a resolved `worldline_tick`.

`dispatch_control_intent_trusted_cbor` and `dispatch_intent_cbor` also
exist in the rlib surface and are ready to use after `init_embedded()`,
but were not exercised by this spike. Scheduler lifecycle control
(`run_until_idle` semantics) remains a follow-up check for G2/G3.

## What this rules out

**The wasm32-unknown-unknown artifact is the wrong embedding target.**

`warp-wasm` also builds to `wasm32-unknown-unknown` for use inside
jedit's browser host. That artifact uses `wasm-bindgen` ABI and requires
a JS host to supply the `wasm-bindgen` imports. A plain `wasmtime` host
cannot satisfy those imports without the full `wasm-bindgen` shim layer.

This is not a bug — it is the correct behavior for the browser build. The
rlib is the correct build for native embedding, and it works perfectly.

**Conclusion:** WARP DRIVE v0.0.1 does **not** need wasmtime.

---

## Performance implications

The read-path overhead for v0.0.1 is:

```
FUSE kernel → handler → CBOR encode → rlib call → CBOR decode → response
```

There is no process boundary, no socket, no wasm interpreter loop. The
CBOR encode/decode is the dominant overhead outside the Echo kernel
itself. This is a substantially better story than the wasmtime approach
originally assumed.
